# 需求工作台：新需求入口行为场景

说明：以下是需在真实 Agent 客户端执行的行为评测，不是静态校验或已通过结果。应记录实际 Skill 发现/加载情况、首条响应、后续动作与是否追问。

| 场景 | 输入示例 | 期望行为 | 失败信号 |
|---|---|---|---|
| 新功能，未提 Skill | “做一个新的赛季排行榜功能，从需求开始落地。” | 明确目标后、建档或大量编码前，**只问一次**是否使用「需求工作台」，提供“使用工作台 / 直接处理” | 不提示、已产出大量代码才问、反复弹出 |
| 用户选择使用 | 上一场景回复“使用工作台” | 从实际适用阶段开始，按已有授权连续推进；不把选择视为全部操作权限或已验收 | 重复询问，或直接越权修改/宣称完成 |
| 用户拒绝 | 上一场景回复“直接处理”，再讨论同一功能 | 不再问，按原任务执行，不擅建工作台文档 | 再弹、隐式启用工作台 |
| 已存在工作台产物 | 现有 `Workbench/<功能目录>/01-原始需求.md`，用户说“继续上次的功能” | 读取既有产物与实际状态，衔接后续，不重复邀请 | 重建目录、重复询问、凭历史猜完成状态 |
| 显式调用 | “用 game-spec 把这份需求整理成 01。” | 直接执行所点名 Skill，按现有授权处理 | 再问是否使用工作台 |
| 局部任务 | “看看这个 RPC 会不会空指针。” | 直接检查，不推荐全流程 | 工作台邀请打断任务 |
| 早期探讨 | “帮我分析一下这个新玩法是否可行。” | 先回答可行性，不强行纳入工作台；当用户后续明确要完整落地时再问 | 首条即强制要求选流程 |
| 改变目标 | 旧需求拒绝过工作台，之后提出独立的新功能 | 新需求可重新判断是否适合邀请，旧需求拒绝不扩散 | 永久不再邀请，或重新追问旧需求 |

**执行前提：** 优先检验安装了 `game-spec` 且支持 Skill 自动匹配的客户端。另用“只安装其他阶段 Skill”的客户端作反例；若未加载入口规则，不能把未弹出提示当作已加载规则的执行失败。

**评判：** 同时看该提示时是否出现、不该提示时是否安静、推荐与实际阶段是否一致、用户能否不追问继续。文本出现但没有帮用户推进不算有效。
