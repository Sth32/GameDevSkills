# game-client-handoff 行为测试

## 1. 全量、增量与销毁

输入：Furnishing Actor 权威持有摆设属性，经 TeapotView 同步；登录/入视野发全量，`placementStatus`、`craftFinishAt` 变化发增量，销毁发移除。

通过：区分权威者与同步组件；写标识、字段类型、枚举、时间单位、全量/增量触发、销毁和重连恢复，足以创建/更新/移除表现。不能只抄字段或设计客户端实体管理器/UI。

## 2. RPC 受理不等于结果

输入：`ReqPlaceFurnishing` 带 `requestId`、位置和摆设类型；同步回包仅受理，最终结果经 `FurnishingPlacementResult` 推送，两处都可能失败。

通过：说明发送时机、参数类型/含义/限制、受理语义、异步关联与两处错误。不能把受理写成成功，也不能漏推送或 requestId。

## 3. 数据不足以支撑表现

输入：客户端需倒计时/进度，Server 只有状态，无起止时间或进度值；文档建议本地固定推算 60 秒。

通过：在相关合同记录服务端缺口，说明重连、延迟、配置变化影响，建议权威时间戳/进度。不能认定固定推算可行、编造字段或设计客户端计时器。

## 4. 只生成合同

输入：Server 已有属性、两个 RPC 和一个推送；用户只要对接文档。

通过：聚焦属性、生命周期、接口和数据充分性，只描述能支持的表现；不设计 UI/MVC/缓存/资源框架，不复述完整需求、调用栈和内部字段方法。

## 5. 可见范围随关系变化

输入：壶主看完整摆设属性，访客只看位置/放置状态；撤销访客权限时实体仍在，Server 视图重算发清除/移除。

通过：写接收范围、字段差异、权限撤销后的清除、实体存在与不可见的区别，以及重连按当前关系全量同步。不能只写“会同步”或让客户端猜关系隐藏规则。
