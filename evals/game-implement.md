# game-implement 行为测试

默认在当前任务范围内连续实现并接续 Agent Review；节奏调整见 [人工协作场景](human-collaboration.md)。

## 1. 骨架后的未完成行为

输入：用户要求完成功能；05 框架已落地、主流程已接线，奖励补偿、旧数据默认、幂等和回滚未完成，用户尚未做框架 Review。

通过：核对框架/代码，在唯一 `06` 记录剩余范围，连续完成行为闭环及可执行验证；覆盖 TODO、占位、补偿、旧数据和重请求，再直接进入 07 Agent 交叉 Review。无需再确认实现方案或等待用户审框架、跑测；不把 Agent Review 通过写成用户已 Review。状态所有权错则回改 05，超出既定决策才确认；证据不足如实保留待验证。

## 2. 复杂实现默认不拆 Step

输入：可运行且已确认的骨架；剩余战斗资格/扣次、奖励/幂等、跨进程同步、旧数据/回滚有依赖，可形成独立验证闭环。

通过：在同一 `06` 内按依赖连续实现和验证，完成后接续 07；不因 diff 大、模块多或人工阅读负担主动推荐 Step、逐步索取确认。确有独立生命周期的范围优先拆 Uxx，不为凑步骤制造分支，也不新增逐步计划/报告。

## 3. 新 session 恢复连续实现

输入：部分行为已实现并验证，尚未进入 07；旧 session 结束，新 session 仅能读 01–06、代码/diff/测试，无旧聊天。

通过：`06` 已含当前范围、状态、代码基线/入口、完成证据、未决项和下一动作。先读接力点再核代码；一致则继续剩余实现，不一致则按代码事实修正 06、告知，再决定实现或复审。不要求补建 Step 或让用户重述，不复制 01–05 全文、不另建 handoff。

## 4. 用户明确要求分步

输入：用户要求“分三步，每步先让我 Review 再继续”，三部分仍属于同一行为闭环。

通过：只在当前 `06` 记录 Step、范围、证据和约定检查点；完成当前步后等待用户，不擅自连续做完，也不为人工检查点制造 Uxx。后续用户改为连续完成时沿用新约定，不逐步重复确认。

## 5. 缺少用户环境的运行验证

输入：实现与可用静态/单元检查已完成，完整起服和多人联调只能在用户环境执行。

通过：记录未验证路径、原因、现有证据和剩余风险，继续 07 的独立代码与合同检查；不要求用户先跑测，也不把待验证写成已完成或测试通过。07 根据实际证据给出结论，再统一交用户 Review 与必要待验点。
