# Skills 设计文档

本项目专注游戏服务端功能开发：需求整理、产品与技术澄清、配置、框架、实现、客户端对接、Review 和长期文档。长期取舍以 [准则](principles.md) 为准，工作单元细节见 [多分支规范](branch-workflow.md)。

## 工作流与职责

```text
01 spec → 02 discovery → 03 tech-clarify → 04 config
  → 05 scaffold → 06 implement → client-handoff（按需）→ 07 review → docs
```

| 技能 | 职责边界 |
|---|---|
| `game-spec` | 整理原始需求，识别独立范围 |
| `game-discovery` | 收敛需要需求负责人决定的产品问题 |
| `game-tech-clarify` | 确认架构、数据、合同等高影响技术决策 |
| `game-config` | 确认配置真源、合法值域、关键值和可写范围，完成验证 |
| `game-scaffold` | 建立数据权威、持久化、同步与基础调用链，不实现产品规则 |
| `game-implement` | 沿框架补齐行为、失败路径、兼容和验证 |
| `game-client-handoff` | 从真实实现提炼客户端所需的数据、属性同步与接口合同 |
| `game-review` | 固定范围并独立评审，修复后原位复审，按风险检查整体集成 |
| `game-docs` | 从已验证实现与 Review 提炼长期稳定契约 |

简单需求不创建 `00` 或 Uxx。复杂功能可从 `01` 开始按独立范围拆分，各单元按真实依赖推进；兄弟分支不用同步阶段。一个单元内部连续实现步骤用 Step，独立交付范围用 Uxx。

## 文档位置

文档位置仅在相关技能执行时解析，不把配置写入 AGENTS.md 或加载到无关对话。每个技能入口包含完整规则，以支持独立安装。

1. 确定目标项目根目录：使用用户指定的目标项目或代码仓库，不能取技能安装目录或任意终端当前目录。多个目标不明确时先确认。
2. 继续已有功能时，先按已提供的文档、阶段引用或 `00` 确定实际功能目录；后续阶段、Uxx、Review、对接与配表说明都在该目录续接。已有同主题长期文档也在原文件更新。
3. 新建文档时，优先使用本次明确指定的位置；否则读取目标项目根目录的可选 `.sth32-game-skills.json`，使用 `documentRoot`；文件或字段不存在时默认 `Workbench`。
4. `documentRoot` 为相对目标项目根目录的非空路径。例如 `{"documentRoot": "Design/Workbench"}`。需要读取的配置若 JSON 格式错误或字段为空、非字符串、非相对路径，应说明问题并停止依赖该配置的新建写入；不得静默回退到其他目录。
5. 按根目录派生 `requirements/<feature>/` 和 `features/<feature>.md`。如果本次明确指定的是功能目录，则直接使用，不能再追加 `requirements/<feature>`；若指定长期文档文件，则直接使用该文件。

只支持项目配置和对话指定，不添加环境变量、个人配置或多层配置搜索。默认不生成配置文件；团队需要自定义时创建并提交 Git。本次临时指定不自动改写项目配置。

改配置只影响新建文档。明确要求迁移已有功能时，才移动文档并同步阶段、索引、对接与长期文档中的实际引用，保持唯一权威位置。若发现同一功能存在多个候选权威目录，先澄清归属，不自行新建第三份。

## 权威文档模型

每个“工作单元 × 阶段”只有一份权威过程文档，保存当前事实、未决项、验证和下一动作。新事实覆盖旧结论，历史由 Git 保存。下游引用上游，不复制完整内容；代码、配置源、测试和日志是实际产物或证据。

所有阶段文档位于同一个已解析的功能目录；新建默认使用 `Workbench/requirements/<feature>/`，配置或对话指定时替换根目录，已有功能沿用原目录：

| 产物 | 单线 | 分支 |
|---|---|---|
| 阶段文档 | `<阶段号>-<阶段名>.md` | `<阶段号>-<Uxx>-<主题>-<阶段名>.md` |
| 客户端对接 | `<主题>-客户端对接文档.md` | `<Uxx>-<主题>-客户端对接文档.md` |
| 单元 Review | `07-交叉评审.md` | `07-<Uxx>-<主题>-交叉评审.md` |
| 整体 Review | 单线 Review 已覆盖 | 有集成风险时使用 `07-交叉评审.md` |
| 工作流索引 | 不创建 | `00-工作流索引.md` |

`00` 只记录 ID、范围、依赖、当前阶段、当前文档和整体 Review 指针，不复制阶段状态正文或业务事实。共享父文档仅保存共享基线；拆分后父单元停止直接推进，叶单元分别继续。

## 阶段状态与衔接

阶段文档顶部状态是唯一状态来源。开始下一阶段前，读取实际依赖的状态与证据；聊天中的“完成”不能替代文档。缺口应说明影响，并按下节的人工约定推进。

| 阶段 | 正常可移交终态 |
|---|---|
| 01 | 叶文档 `整理完成`；共享父文档可为 `已拆分` |
| 02、03 | `已收敛` |
| 04 | `已完成` |
| 05 | `骨架已完成` |
| 06 | `已完成` |
| 07 | `通过`；`有条件通过` 仅按明确接受的条件继续 |

结束前核对元信息、正文、验证与下一动作，清除互斥或过时结论，更新真实终态并重新读取确认落盘。证据不足不得宣布完成。客户端对接以合同充分性与真实可达性为完成依据，长期文档以稳定契约与最后核对版本为依据，不另造阶段终态。

## 人工协作

用户可调整阶段顺序、合并确认、按显式假设先行、延后 Review 或约定集中回写。已有适用授权直接执行；范围、风险或假设实质变化时再沟通。跳步和继续约定不替代实际操作权限。

继续决定不等于需求已确认、测试通过或 Review 通过。有缺口时在当前文档按需记录一行：

> 继续约定：<范围>；依据/假设：<内容>；待补：<决策或验证>；复核点：<何时检查>

不新增审批文件或状态体系。单 reviewer、人工 Review 或延后交叉检查时如实说明覆盖，不能宣称完成未执行的独立验证。用户指定先写长期文档时，仅从已验证稳定事实写草稿，并在交接说明中指出 Review 覆盖限制。

各技能入口直接包含必要协作规则，使单独安装仍可执行；按职责编辑技能与模板，不依赖同步脚本或生成提交。

## 文档更新与变更传播

新事实改变当前阶段时，默认同轮原位更新并告知路径；用户约定集中回写时按约定执行，交接时说明未落盘内容。上游有误时列出受影响文档与拟修改内容，已有适用授权直接回写，超出授权再确认。

范围、阶段状态、接口/RPC/事件合同、数据权威、工作单元依赖或配置真源变化时，核对：

- 当前文档元信息、正文、验证、阻塞与下一动作；
- 已有且真实依赖该事实的上下游文档与客户端合同；
- `00` 中的路由和 Review 指针。

修正实际受影响内容，只使对应 Review 失效，不机械传播到无关分支。未传播完成时明确说明缺口。

## 配置、对接与 Review

配置执行状态、人工填表步骤和验证结果都写在当前 `04`；策划配表说明是按需交付物，不是第二份权威执行清单。客户端对接按单元独立进行，共享合同引用共同基线，各单元仅记录新增或变化合同。

当前单元及真实依赖达到条件后即可独立 Review。所有目标叶单元通过后，仅在共享代码/数据、状态机、配置表、RPC/事件、客户端合同或发布顺序等存在组合风险时执行整体 Review。整体评审复用分支证据，发现问题路由回所属单元，不重做所有内部检查。

## 长期功能文档

`game-docs` 保留为交付环节。已有同主题长期文档在原文件更新；新建按文档位置规则写入 `<文档根目录>/features/<feature>.md`，默认 `Workbench/features/<feature>.md`。临时指定过程目录不会隐式改变长期文档目录。

以当前实现、相关分支 Review 和必要的整体 Review 为依据，记录职责、稳定规则、数据权威与跨模块合同。按最终系统语义组织，不复制 Uxx 拓扑、阶段状态、配置快照、待办或过程历史；文档注明最后核对版本。

## 验证

`python scripts/validate_skills.py` 检查技能元信息、随包引用、核心流程入口和仓库文档链接；单元测试验证检查器能识别资源缺失和越界引用。GitHub Actions 执行只读校验，不生成或提交文件。

`evals/` 保留技能、多分支、阶段衔接、变更传播和人工协作的行为场景。场景需以实际执行证据判定，静态标记齐全不代表行为已通过。
