# 人工协作约定

这份约定说明如何在现有 `01–07`、工作单元、客户端对接和轻量维护路径中协作。保留现有 skill 名称、阶段职责、文件命名和项目自己的工作方式，不要求迁移历史文档。

## 默认检查与人工调整

阶段门禁、Step review、方案确认、上游回写、文档时序和 reviewer 数量都是默认协作方式。用户可以用自然语言指定跳过、并行、合并确认、延后验证或集中回写；不需要特殊口令、审批表或重复确认。具体指令和仍适用于当前任务的既有授权优先于各 skill 与模板中的默认暂停规则。

Agent 先核对能自行查到的事实。发现缺口时简短说明缺什么、影响什么、建议如何继续；用户已明确接受相应范围或假设时直接执行。允许继续依赖暂定结论的可回退实现或草稿工作，不把人工调整限制成“只能调查”。同一决定不重复询问；只有范围、风险或假设发生实质变化时重新沟通。

## 如何表达继续工作的决定

以下都是有效指令，按用户指定范围理解：

- “这次先不补 02，规则按刚才确认的做，直接进入 03。”
- “先按 A 假设实现，策划明天确认后再调整。”
- “Step 1 到 3 连续做完，最后我统一 Review。”
- “已确认的产品结论直接回写 01，不用再问一次。”
- “客户端测试我来做，你先完成服务端部分并列出待测点。”
- “先用一个 reviewer，正式交叉 Review 留到合入前。”
- “本轮文档最后统一更新，继续实现。”

宽泛的“继续”只覆盖已说明的下一步，不自动授权新范围、发布或数据处置。用户尚未决定的产品规则可以作为显式假设继续可回退工作，不能写成已确认需求。

## 继续工作与证据结论分别记录

用户允许继续，不代表测试通过、需求收敛或 Review 通过。保留原有阶段状态词；有缺口时在当前文档按需补一行：

> 继续约定：<用户决定与范围>；依据/假设：<一句>；待补：<验证或决策>；复核点：<何时再看>

不另建审批文档，不增加新的状态体系。轻量维护未要求留档时，在回复里说明即可；跨会话需要恢复时，将约定放入用户认可的现有记录。约定被完成或新决定替代后原位清理，避免长期堆积。

## 哪些事情需要停下当前动作

只有会实际发生且尚未获得相应授权的破坏性写入、生产发布、资产/数据处置，或工具明确缺少权限时，才暂停受影响动作并说明原因。继续完成其他已授权工作，不把局部限制扩大成整个任务停摆。

人工可以决定研发顺序、接受已说明的风险和推迟 Review；不能把缺失证据改写成成功，也不能用“绕过门禁”替代实际操作权限。具体资产、数据和发布动作按项目机制及已有明确授权执行。

## 文档与 Review 的弹性

默认同轮更新当前文档；用户要求集中回写时，按约定边界更新，交接或会话结束前告知尚未落盘的信息。已授权的上游回写直接执行并告知变化，不重复请求同一确认。

正式交叉 Review 默认保留独立视角。用户可指定单 reviewer、人工 Review 或延后部分检查；如未实际执行完整交叉验证，就说明覆盖范围，保留“评审中”或相应事实结论，不能宣称完整交叉 Review 已通过。用户可以继续后续工作。

用户要求在 Review 前整理长期文档时，可以从已验证的稳定事实先写草稿，未确认契约留在过程文档；Review 覆盖限制在交接说明中告知，不把阶段状态塞进长期文档。

## 维护方式

本文件是协作约定的维护源。`scripts/apply_stage_transition_policy.py` 将其同步到各 skill 的 `references/协作约定.md`，使单独复制一个 skill 后仍可使用。入口只保留短规则，遇到门禁、授权或交接问题时再阅读完整约定。
