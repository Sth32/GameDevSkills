# 澄清游戏程序实现

**人工协作优先：以下门禁、确认点和文档时序均为默认方式；用户可跳步、合并确认、按显式假设继续或延后 Review，已有适用授权无需重复确认。执行前说明实际缺口与影响，按约定范围继续，不把未验证写成已通过；真实操作权限仍须满足。遇到暂停、上游回写或交接时，按[协作约定](references/协作约定.md)处理；该约定也适用于下文模板。**

## 目标

基于当前工作单元适用的需求基线、当前工作单元实际依赖的需求挖掘文档、代码架构和现有实现，向负责程序确认会显著影响架构、数据、接口、风险或验证方式的实现决策，并维护未分支的 `03-程序实现澄清.md`，或当前工作单元的 `03-Uxx-<主题>-程序实现澄清.md`。

**核心原则：先查明事实，只讨论高影响决策；问题越往后越少。**

**跨边界通信合同硬限制：只要当前工作单元跨实体、线程、进程或 Server/Client 边界，03 必须把关键事实按最小合同矩阵澄清：事实/数据、权威拥有者、内部路由、客户端是否可见、传输载体、标识类型、生命周期。内部 Host/View、路由镜像或服务端方法不得因为名称相似就被推断成客户端可见合同；无法从 Schema/Defs/生成物/注册点或实际调用链证明的能力必须保持未确认。**

**文档职责：当前 `03` 只保存当前工作单元有效的高影响实现决策、尚未解决的高影响技术问题，以及已经发现但尚待用户确认修订上游文档的最小阻塞说明。产品规则留在当前工作单元适用的需求基线，未解决产品问题留在对应 `02`，不得跨文档长期重复。**

**邻接硬限制：一个实现事项的决策、必要依据、选项、结论和关键影响必须放在同一个连续分块。** 不得按“模块、数据、接口、失败、发布、验证”等维度把同一决策拆到多个摘要章节。

**结构硬限制：正文默认只有“实现事项”一个固定二级标题。** 禁止再建立“实现决策摘要、当前批次、问题台账、局部默认、阻塞与延期、收敛检查”等重复分块。

**闭环硬限制：每轮沟通结束后立即原位重写当前阶段事项。** 决策确认后，用精简结论替换问题、选项、推荐和回答记录；删除已失效、被覆盖或不再有用的内容。

**分支工作流硬限制：工作单元最早可在 `01` 需求整理阶段创建，并可独立推进到客户端对接和 `07-Uxx` Review；不存在“所有分支先汇合才能 review”的门禁。当前阶段若发现真实独立范围，仍可继续拆分稳定工作单元 `U01`、`U02`……；所有文件保持在同一个 `docs/requirements/<feature>/` 目录，不增加分支子目录。没有真实分支时继续使用原文件名。第一次拆分创建 `00-工作流索引.md`，只记录 ID、范围、依赖、当前阶段、当前文档和整体 Review 指针；拓扑只由依赖表达。分支文档命名为 `03-<Uxx>-<主题>-程序实现澄清.md`。当前 Uxx 只检查自己的共享需求基线、自身/祖先需求文档和真实依赖；无依赖兄弟工作单元不构成阻塞。**

在分支工作流中，下述“本阶段唯一文档”指**当前工作单元在本阶段的唯一权威文档**；同一阶段可以存在其他工作单元的 `03` 文档。`00-工作流索引.md` 是路由元数据，不属于某个工作单元的阶段正文。

**文档更新时序硬限制：任何新事实、确认、执行结果或验证结果只要改变本阶段内容，必须在同一轮立即原位更新本阶段唯一文档，并明确告知用户已更新的文件路径；不得等到阶段结束、批次结束或用户再次提醒。发现结论会改变更早阶段文档时，必须主动说明受影响文档和拟修改内容，先获得用户确认，再更新上游文档；未确认前不得静默改写。**

**结构性变更影响传播硬限制：当范围、阶段状态、接口/RPC/事件合同、数据权威、工作单元依赖或配置真源发生变化时，必须在同一轮执行影响扫描，不得只修当前局部段落。当前阶段文档内至少核对顶部元信息、相关正文规则/矩阵、验证结论、阻塞与下一动作；同时定位已有且实际依赖该事实的上下游阶段文档、客户端合同与 `00-工作流索引.md` 中的旧引用。当前阶段和本 skill 允许直接维护的下游内容立即原位更新；若受影响的是需要用户确认才能改写的上游文档，必须明确列出受影响文件、旧事实与拟修改内容并等待确认，不得静默遗漏，也不得把未传播完成的结构性变化描述为已闭环。**

**阶段完成一致性硬限制：在宣布本阶段完成、确认或移交前，必须对本阶段权威文档做一次一致性收敛。同一事项不得同时保留互斥的当前状态、数值、操作要求或验证结论；发现冲突时，必须依据最新用户确认、实际源、代码或配置、生成物以及验证证据判定唯一当前事实并原位改写，删除被覆盖、错误、过时或仅用于过程追踪的内容。若证据不足无法判定，则该事项保持未完成或阻塞，只保留唯一待确认点，不得以“已完成”结束阶段。**

**维护升级入口硬限制：本 skill 允许从轻量维护独立进入。若本次任务没有适用的完整前序阶段文档，先用用户已确认目标、当前代码/配置、稳定合同与验证证据建立升级基线，并检查本阶段真正需要的产品、技术、配置或框架事实。已由证据覆盖的前序阶段不补建文档、不伪造完成状态；首次进入时在当前阶段唯一文档记录入口、范围、代码基线、证据位置、必要的已确认结论与实际未决项，后续阶段引用这一基线。下文文档职责、输入、上游回写和完成条件中的缺失文档按该基线承接：新确认事实原位归入基线，已有适用正式文档仍按原规则维护。若仍缺少会改变本阶段工作的产品/技术决策或运行证据，返回最早必要 skill 解决，不得把未知当成已确认。已有且适用于本次任务的上游文档仍保留真实状态；用户可按协作约定接受显式假设、先行实现或延后检查，不把这些决定当作前置已通过。该入口不自动创建 Uxx。**

**阶段切换门禁硬限制：默认读取当前范围真实上游的状态与证据，达到本阶段条件后写入原有终态并核对落盘。缺文件、状态滞后或检查未完成时，先说明缺口及影响；用户可按协作约定跳步、并行、采用暂定假设或延后检查，也可预先授权连续执行多个 Step，Agent 按约定范围继续，不重复索要同一确认。继续决定与验证结论分开：保留未完成/待验证事实，在当前文档按需记录继续范围、依据或假设、待补项与复核点，不新增审批文档。只有未授权的高后果实际操作或缺少工具权限才暂停该动作；不因形式状态单独阻塞其他已授权工作。**

存在 `00` 时，上述门禁必须先从索引解析目标 `Uxx` 的共享上游和直接前驱，只检查真实依赖；未被依赖的兄弟工作单元不构成阻塞。索引无法唯一确定目标工作单元、依赖或当前文档时，先修正索引，不得从聊天记忆猜测。

**内置记录硬限制：每次逻辑上的文档变更完成后，只执行当前 skill 自带的 `scripts/document_record.py append`，提交本次变更的最小结构化事实；写入器完整实现随 skill 分发，但记录数据仍存放在仓库外。普通开发 Agent 必须把写入器当作只写接口：不得打开、读取、搜索或修改写入器源码，不得查找、定位、读取、搜索、解析或直接修改任何历史记录或记录文件，也不得为了写记录扫描工作区中的 record 文件。同一原因、同一轮的原子变更只提交一次，携带实际变化文档、trigger、reason、change summary、validation、outcome 与必要 feedback；正常进度不得虚构问题、根因或预防建议。用户改变需求使用 `user_change`，用户指出 Agent/文档错误使用 `user_correction`。写入器不可用或失败时，明确报告记录未写入，但不得通过 shell 重定向、通用文本 API 或直接文件操作绕过写入器。**

创建或修改 `00-工作流索引.md` 也必须按本 skill 的同一记录规则追加 `record.jsonl`；普通 `03` 正文变化若不改变拓扑、当前阶段或当前文档，不重复修改 `00`。

## 产物与前置

未分支时必须读取：

- `01-原始需求.md`；
- `02-需求挖掘.md`。

存在 `00` 时，先定位当前 `Uxx`，再读取当前工作单元适用的需求基线、当前单元的共享上游与直接前驱，以及索引声明的实际 `02` 依赖。若仍有会改变当前工作单元实现方向的 P0/P1 产品问题，立即在当前 `03` 记录最小阻塞状态并告知用户，然后按上游文档确认流程回到对应 `game-discovery`；不得静默修改 `01` 或任一 `02`。

未分支时维护：

```text
docs/requirements/<feature>/03-程序实现澄清.md
```

分支后当前工作单元维护：

```text
docs/requirements/<feature>/03-<Uxx>-<主题>-程序实现澄清.md
```

使用 [程序实现澄清模板](references/程序实现澄清模板.md)。文档表示当前实现决策，不保存采访流水。

若在本阶段发现当前范围应继续拆分：

1. 首次分支先创建 `00-工作流索引.md`，已有索引则原位更新；
2. 给所有直接后继分配新的稳定 `Uxx`；
3. 当前父 `03` 压缩为仍有效的共同决策基线并标记 `已拆分`；
4. 分支专属待确认项和已确认决策移入对应子 `03`，共享内容只引用父基线；
5. 父工作单元不再直接进入 `04`，只有索引中的叶子后继继续推进。

## 什么应该问程序

只询问会改变以下内容的高影响决定：

- 模块归属和跨系统责任；
- 持久化、迁移、历史数据兼容；
- 并发、一致性、幂等和跨进程时序；
- 协议、公共接口和上下游契约；
- 失败、补偿、回滚和灾难恢复；
- 发布、灰度、开关、降级和关键验证；
- 存在真实风险时的容量和性能约束。

不要询问变量、函数、类、文件命名，普通局部代码写法，可由代码直接确认的事实，或不影响公共契约、数据安全和维护成本的微小偏好。

## 工作流程

### 1. 定位当前工作单元与产品边界

存在 `00` 时先读取索引，确认当前 `Uxx`、范围、依赖和当前文档；没有 `00` 时按单线处理。读取已确认规则、对应 `02` 的未决项、明确排除、延期项和重大风险。程序澄清不得重新定义产品目标；发现产品矛盾时，不得直接修改上游文档。

先立即更新当前 `03`，在最相关事项内写明阻塞事实及受影响的上游文档，并告知用户具体路径。随后主动说明拟对当前工作单元适用的需求基线 或对应 `02` 做出的具体修改，获得用户确认后再调用 `game-spec` 或 `game-discovery` 更新；上游更新完成后，立即清理当前 `03` 中已解除的临时阻塞并再次告知用户。

### 2. 调查代码与架构

检查当前工作单元相关模块、数据模型、状态流转、配置、协议、同类实现、失败处理、测试、发布方式和兼容约束。

能从环境确认的事实直接用于分析，不把代码阅读问题转问负责人，也不写成长篇现状报告。若调查证明两个范围可以独立推进且当前文档会造成独立阻塞互相干扰，应优先拆工作单元而不是继续在一个文档中扩张。

### 3. 筛选高影响决策

事项只有同时满足以下条件才进入当前文档：

1. 现有代码和约定无法给出可靠答案；
2. 答案会改变架构、公共契约、持久化数据、故障安全、发布方案或显著工作量；
3. 现在决定比编码中临时决定更便宜；
4. 负责程序拥有决定权；
5. 不是未解决产品问题的伪装；
6. 属于当前工作单元范围。

P0 表示不可逆数据/协议、架构阻塞、一致性正确性或重大线上风险；P1 表示重要边界、失败恢复、迁移发布或验证路径；P2 仅在维护影响确实值得记录时保留。

### 4. 按事项聚合

每个待确认事项最多包含：ID、优先级、状态、一个可直接决定的问题、必要代码/架构依据、最多三个真正不同的方案及一条推荐。属于同一决策的模块、数据、接口、风险和验证影响必须相邻，不能分别建章。

### 5. 分批沟通

每批处理 1–3 个强相关事项，按当前工作单元内部依赖顺序推进。后一批应更少、更聚焦；不因检查表还有项目就继续追问。

### 6. 回答后原位压缩

收到回答后，在同一轮完成：

1. 将原事项改写为“已确认”状态；
2. 用一句明确结论替换原问题、选项、推荐和回答记录；
3. 只保留会指导当前工作单元后续实现的关键影响；
4. 删除讨论过程、被否决方案、失效依据和重复描述；
5. 部分解决时只保留剩余决策分支；
6. 已取消、已默认或不再高影响的事项直接移除；
7. 同步更新或移除因该答案失效的其他事项；
8. 在回复中明确告知当前 `03` 的完整路径已更新。

若答案同时证明当前工作单元适用的需求基线或某个实际依赖 `02` 已过时，说明受影响文件和拟修改内容。已有适用的结论确认与回写授权时直接更新；仅对未获授权的新变化询问。更新后告知路径，清理当前 `03` 中临时的上游阻塞状态。

### 7. 更新路由元数据

只有新建/拆分/终止工作单元、依赖变化、当前阶段或当前文档变化时更新 `00`。不得把技术决策、P0/P1 数量或阶段顶部状态复制进索引。

## 收敛条件

对当前叶工作单元：

- 无未解决 P0/P1 实现问题；
- 无尚待用户确认修订的上游文档阻塞；
- 当前范围核心边界、数据、契约、失败路径和兼容策略明确；
- 发布与回滚不存在未归属重大风险；
- 关键验证方式足以证明当前工作单元实现正确；
- 当前 `03` 中没有重复摘要、旧问答或失效方案。

结束时只更新当前文档顶部状态并说明该工作单元能否进入配置阶段，不生成额外决策摘要。一个工作单元收敛不要求兄弟分支同步，也不代表整个功能可以进入 `game-review`。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 同一决策分别写进模块、数据、接口和风险章节 | 把相关内容放进同一个事项分块 |
| 同时保留决策摘要、当前批次和问题台账 | 每个事项只出现一次 |
| 回答后保留原问题、三个方案和完整回复 | 原位压缩为结论与关键影响 |
| 把代码阅读问题转问负责人 | 先调查，只有高影响决策才问 |
| 产品问题未解决却用技术默认值顶上 | 立即更新当前 `03` 标记阻塞，再确认后修订上游文档 |
| 发现上游错误后直接改 `01` 或 `02` | 先告知拟修改内容并获得用户确认 |
| 只在聊天中说明新决策 | 同一轮更新当前 `03` 并明确告知路径 |
| 越问越细、永不结束 | 以后续决策价值和收敛条件停止 |
| 为分支创建子目录 | 所有 `Uxx` 文档与 01/00/07 保持同目录 |
| 用 U01.1 表示子分支 | 分配新的 Uxx，依赖只写在 00 |
| 兄弟分支未完成就阻塞当前 Uxx | 只检查当前工作单元的实际依赖 |
| 父工作单元拆分后仍直接进入 04 | 父 `03` 标记已拆分，仅叶子后继继续 |
