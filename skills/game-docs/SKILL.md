# 游戏模块权威文档

**人工协作优先：阶段门禁、确认点与文档时序是默认方式。用户可跳步、合并确认、按显式假设继续或延后 Review；已有适用授权不重复确认，真实操作权限仍须满足。继续决定不等于验证通过：在过程文档或交接说明中保留实际缺口、依据或假设、待补项与复核点；本规则也适用于随包模板。**

## 文档位置

- 只在本技能执行时读取目标项目根目录的可选 `.sth32-game-skills.json`；`documentRoot` 是相对该项目根目录的非空路径。项目根目录取用户指定的目标项目或代码仓库，不是技能安装目录或终端当前目录；目标不明确时先确认。
- 新建文档按“本次明确指定 → 配置中的 `documentRoot` → `Workbench`”选择位置。用户直接指定功能目录时直接使用，不再追加 `requirements/<feature>`；其余情况下过程文档放在 `<文档根目录>/requirements/<feature>/`，长期文档放在 `<文档根目录>/features/<feature>.md`。直接指定长期文档文件时使用该文件；仅指定过程功能目录不改变长期文档目录。
- 继续已有功能时，阶段、Uxx、Review、对接和配表说明都沿用已有功能目录；已有同主题长期文档沿用原文件。改变配置不自动搬迁或复制文档，只有明确要求迁移才移动并更新引用。下文路径示例仅用于新建。
- 未提供文件或字段时使用默认值，不自动创建配置。需要读取的配置若 JSON 格式错误或字段为空、非字符串、非相对路径，说明问题并停止依赖该配置的新建写入，不静默回退。只支持项目配置与对话指定，不读取环境变量或个人配置，也不把设置写入 AGENTS.md。

## 目标

从当前已实现代码中提炼一份简洁、稳定、可长期信任的模块文档，使维护者能够快速回答模块职责、核心规则、数据权威与持久化、关键协作契约和不可破坏约束。

**核心原则：分析可以深入，落盘只保留长期稳定的系统契约。**

**单文档硬限制：同一功能或模块只能存在一份权威实现文档。** 不得另建架构摘要、数据说明、接口手册、实现复盘、维护清单、FAQ、`v2` 或 `final` 平行版本。已有内容必须原位重写；代码注释、测试、协议定义和配置源属于事实来源，不算旁支权威文档。

**分支 Review 输入规则：过程工作流若存在 `00-工作流索引.md`，必须用它定位全部实际工作单元，并确认本次纳入长期文档的叶工作单元都已完成各自 `07-Uxx-*` Review。整体 `07-交叉评审.md` 仅在确有集成风险时存在；存在则必须达到可交付终态并作为额外证据，不存在不得单独成为阻塞。`00` 只用于定位材料，不得把 Uxx、DAG、阶段状态或任务进度写入长期权威文档。**

**文档更新时序：新事实改变本阶段内容时，默认同轮原位更新唯一文档并告知路径；用户约定集中回写时按约定执行，交接时说明未落盘内容。需要修正上游时列明影响和拟修改内容，已有授权直接回写，超出授权再确认。**

**结构性变更影响传播：范围、状态、合同、数据权威、依赖或配置真源变化时，核对当前文档元信息、正文、验证与下一动作，并同步真实受影响的上下游、客户端合同和 `00-工作流索引.md`；不扩散到无关分支。**

**完成前一致性检查：依据当前实现与验证证据，清除互斥或过时契约；未确认内容留在过程文档或交接说明，不写成长期权威结论。**

**阶段切换门禁硬限制：生成或更新长期功能文档前，必须读取本次范围适用的单线或分支 Review 顶部状态；需要整体 Review 时也检查其状态。未达到可交付终态时说明具体缺口；用户要求先整理时可从已验证的稳定事实编写草稿，在交接说明中保留 Review 覆盖限制，不替上游补写通过状态。长期文档自身不是阶段过程文档，不写阶段状态、未解决计数或当前步骤，也不要求模板定义终态；完成时核对稳定契约、更新最后核对版本并重新读取确认内容已落盘。**

本阶段的实际前置是：未分支时单线 `07-交叉评审.md` 已完成；已分支时本次范围所有叶工作单元的 `07-Uxx-*` 已完成。整体 `07-交叉评审.md` 若存在也必须完成，但它不是分支模式的强制前置。长期文档不复刻分支结构。

文档描述当前生效的系统事实，不是代码导读、实现复盘、评审报告、分支拓扑、排查记录或任务清单。

## 输入与默认产物

读取：

- 当前代码、属性定义、RPC、持久化、配置消费点和测试；
- 未分支时的 `07-交叉评审.md`，或分支模式下全部相关 `07-Uxx-*` 的最终结论；整体 `07-交叉评审.md` 若存在也一并读取；
- 若存在 `00-工作流索引.md`，用它定位所有与最终实现有关的 `Uxx` 文档和共享上游；
- 若未分支，读取 `01-原始需求.md` 至 `06-完整实现方案.md` 中实际仍有解释价值的结论；
- 项目既有文档结构、命名和索引约定；
- 当前提交或可确认版本标识。

分支模式下，不机械拼接所有 Uxx 文档正文。优先级仍是当前代码与已验证证据；过程文档只用于解释为什么某个稳定契约存在、帮助发现遗漏或冲突。

已有同主题长期文档时沿用原文件；新建时按“文档位置”规则解析根目录，写入：

```text
<文档根目录>/features/<feature>.md
```

使用 [功能实现文档模板](references/功能实现文档模板.md)。已有同主题文档时原位重写，不新建平行版本或拆分子文档。

## 事实优先级

材料不一致时，以当前系统真实行为为准：

1. 当前可运行代码与属性、协议定义；
2. 已验证测试和运行证据；
3. 当前范围全部有效的分支 review 结论，以及存在时的整体 review 最新结论；
4. 分支/共享实现方案与澄清文档；
5. 当前工作单元适用的共享/专属需求基线和早期讨论。

方案与代码不一致时，本阶段权威文档记录实际实现并立即更新。若该不一致说明某个 `Uxx` 或共享过程文档已经过时，不得顺手改写；必须明确指出具体文档和拟修改内容，获得用户确认后再更新。

历史原因只有在仍约束未来修改时才保留。不确定信息不得写成权威结论。

## 应该记录什么

### 1. 职责与边界

用少量文字说明模块解决什么、权威所有者是谁、主要消费者是谁、复用什么既有机制、不负责什么。不重写完整需求，不描述工作单元如何拆分。

### 2. 核心规则

只记录决定外部行为或约束未来修改的规则，例如资格成立/失效、共享公共判定、状态重算、不能混淆的关系、顺序/幂等/唯一性/失败语义。先写系统结论，再说明原因或影响。

### 3. 数据与持久化

对关键属性和状态说明权威所有者、是否持久化、镜像与同步、运行时派生。即使这些事实原先来自多个 Uxx，长期文档也按系统语义合并，不按 Uxx 分章。

### 4. 关键协作契约

记录跨模块/实体/端的稳定合同：属性同步方向和生命周期、RPC/事件时机与语义、公共判定/唯一事实来源、配置控制内容和稳定消费入口。

### 5. 修改约束

只保留少量不写就容易产生隐蔽错误的不变量。普通实现细节、通用规范、分支状态、DAG 和 task progress 不写。

同一系统事实只描述一次；如果多个工作单元最终实现同一个系统契约，应在长期文档合并为一个结论，而不是保留 Uxx 视角。

## 禁止写入

默认删除：

- `U01/U02` 等工作单元 ID、`00` DAG、阶段状态与任务进度；
- 配表当前值、行号、资源数值、时长、耐久和概率等可调参数；
- TODO、待办、延期项和后续优化建议；
- 临时 bug、修复过程、排查日志、测试记录；
- 完整文件清单、逐函数说明、长调用链；
- “本次新增/修改了什么代码”的实现汇报；
- 分支拆分理由、并行/串行执行历史、review 流水；
- 可从类型、命名和局部实现直接推断的内容；
- 与主文档竞争权威性的平行文档。

数字标识仅在属于跨系统协议、存档或兼容契约时保留。

## 工作流程

### 1. 验证 Review 覆盖

先查找 `00-工作流索引.md`：

- 不存在：确认单线 `07-交叉评审.md` 已达到可交付终态；
- 存在：确认本次范围所有叶工作单元都有已完成的 `07-Uxx-*` Review；若 `00` 指向整体 `07-交叉评审.md`，也确认其达到可交付终态；若 `00` 明确 `整体 Review：不需要`，不得因为没有整体 07 而阻塞。

不满足时明确指出具体未完成工作单元或 Review。默认先补齐 Review；用户要求先整理时，可从已验证的稳定事实编写草稿，在交接说明中指出覆盖限制，不把未知合同写成权威结论，也不替上游补写通过状态。

### 2. 确定模块边界

从当前代码的数据所有权和外部行为反推模块边界，查找已有同主题长期文档并选择唯一权威文件。边界确认或变化后立即更新并告知用户。

### 3. 从代码重建事实

检查入口、状态变化、属性定义、持久化、镜像同步、RPC、事件、配置消费和失败语义。若存在多个 Uxx，只把它们当定位线索，不能把“分支文档都写了什么”当系统事实本身。

每获得足以改变权威文档的可靠事实立即原位更新。

### 4. 提炼稳定契约

候选内容需通过：半年后仍大概率成立；不记录会增加破坏语义风险；它描述代码之外仍需要明确的契约。未通过则删除或留在代码/测试/issue/review。

### 5. 过滤临时、分支与重复信息

主动移除配置快照、任务状态、实现证据链、修复记录、普通代码细节以及 `00/Uxx` 拓扑。多个 Uxx 最终形成的同一契约只保留一处系统级表述。

若其他长期文档与本权威文档重复，应合并必要稳定契约并删除或废弃重复文档；涉及过程文档时先说明拟修改内容并获得用户确认。

### 6. 原位重写与最终压缩

已有文档重复、过时或粒度过细时直接删除和重写对应章节。相同结论只出现一次；同一问题相关信息尽量相邻；没有实质内容章节直接删除。每次内容变化后立即告知路径。

## 默认文档结构

```markdown
# <功能或模块名>

> 最后核对：<commit / 日期>
> 权威入口：`path/to/authority`

## 职责与边界
## 核心规则
## 数据与持久化
## 关键协作
## 修改约束
```

章节不是必须全部出现。简单模块可以很短；不因为前期有多个工作单元就按工作单元分章。

## 完成前检查

确认文档能回答模块职责、唯一事实来源、核心规则、数据持久化/镜像、主要协作入口、关键不变量；并确认：

- 没有配置快照、TODO、实现过程、分支拓扑或任务状态；
- 没有完整文件目录或重复调用链；
- 没有与本文件竞争权威性的平行文档；
- 每个现状结论都能在代码、属性定义或测试中找到依据；
- 当前范围的单线或各分支 Review 已达到可交付终态；需要整体 Review 时也已完成；
- 没有未经用户确认而被改写的过程文档；
- 文档已经压缩到继续删除会损害理解或修改安全的程度。

## 完成条件

- 项目内存在唯一、可发现的模块权威文档；
- 文档以当前实现为准，并注明最后核对版本；
- 职责、规则、数据权威、持久化、同步和关键协作清楚；
- 不包含 `00/Uxx` 流程拓扑、配置快照、任务状态、实现复盘或易过期细节；
- 已确认本次范围全部叶工作单元分别 Review 完成，且需要时整体 Review 也已完成；
- 无尚待用户确认修订的上游文档阻塞。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 把 U01/U02 作为长期文档章节 | 按最终系统职责与契约合并，而不是保留开发拓扑 |
| 当前范围仍有未完成 Review 就生成长期文档 | 完成相应单线/分支 Review；整体 Review 仅在需要时执行 |
| 调查完成后才一次性重写文档 | 可靠事实改变当前内容时同轮更新 |
| 发现过程文档过时后直接改写 | 先列明具体文档与拟修改内容，获得确认后更新 |
| 为修订结果创建 v2/补充文档 | 原位重写唯一权威文档 |
