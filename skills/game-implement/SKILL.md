# 完成游戏功能实现

**人工协作优先：阶段门禁、确认点与文档时序是默认方式。用户可跳步、合并确认、按显式假设继续或延后 Review；已有适用授权不重复确认，真实操作权限仍须满足。继续决定不等于验证通过：在当前文档保留实际缺口、依据或假设、待补项与复核点；本规则也适用于随包模板。**

## 文档位置

- 只在本技能执行时读取目标项目根目录的可选 `.game-dev-workbench.json`；`documentRoot` 是相对该项目根目录的非空路径。项目根目录取用户指定的目标项目或代码仓库，不是技能安装目录或终端当前目录；目标不明确时先确认。
- 先通过已提供文档、阶段引用、`00` 或项目内同功能文档定位已有功能目录；后续阶段、Uxx、Review、对接和配表说明都在原目录续接，跨天或修改配置也不另建目录。多个候选权威目录无法确定归属时先澄清；只有明确要求迁移才移动并更新引用。
- 确需新建功能目录时，按“本次明确指定 → 配置中的 `documentRoot` → `Workbench`”选择根目录，直接使用 `<文档根目录>/<YYMMDD><feature>/`，不添加 `requirements/`、`features/` 或 Uxx 子目录。用户直接指定功能目录时原样使用，不再追加日期或功能名。
- `YYMMDD` 为功能首次建档时的用户当地日期（两位年、月、日），与稳定功能名直接相连，例如 `Workbench/261030策牌Q4优化/`。已给出带日期的功能目录名时沿用，不重复加日期；后续阶段沿用首次目录。下文路径示例仅用于新建。
- 长期文档优先原位更新已有同主题文件；没有时在当前功能目录创建 `08-功能实现文档.md`，与过程文档同目录。`08` 只用于文件排序，不增加阶段状态或门禁；明确指定长期文档文件时使用该文件。
- 未提供文件或字段时使用默认值，不自动创建配置。需要读取的配置若 JSON 格式错误或字段为空、非字符串、非相对路径，说明问题并停止依赖该配置的新建写入，不静默回退。只支持项目配置与对话指定，不读取环境变量或个人配置，也不把设置写入 AGENTS.md。

## 目标

基于当前工作单元已确认并可运行的框架，补齐需求细节、失败路径、兼容与验证；根据实现规模选择一次完成或分步骤实现，控制单次人工 review 负担；持续维护未分支的 `06-完整实现方案.md`，或当前工作单元的 `06-Uxx-<主题>-完整实现方案.md`，使新的 session 能从当前文档、实际依赖与代码安全接力。

**核心原则：沿既定框架完成行为闭环；复杂实现按可 review 的纵向闭环分步推进；真正可以独立推进的范围拆工作单元；发现框架根因问题时修订框架，不在细节层堆补丁。**

**真实消费链验证硬限制：对本工作单元实际涉及的接口、配置、权限、异步或持久化路径，不能以“定义存在/代码已写/测试局部通过”作为闭环。应按风险追踪真实链路：定义/配置真源 → 生成/注册 → 暴露或寻址 → 权限检查对象 → 最终执行对象 → 运行时消费/副作用 → 状态生命周期 →异步与失败路径 → 持久化/重启恢复 → 发布/回滚；只检查当前功能实际经过的节点。重点证明授权对象与执行对象一致、旧异步回包不会覆盖新状态、target missing/closing/expire 等终态能封口、时间事实使用一致时钟，以及 rollback 是可执行路径而非文档口号。缺少关键证据时保持未完成或显式风险。**

**单文档硬限制：当前工作单元在本阶段只能维护一份完整实现方案过程文档。** 不得为同一工作单元的不同实现步骤另建实施计划、步骤文档、需求矩阵、测试报告、验证清单、上线说明、风险清单或完成总结。不同工作单元可分别拥有自己的 `06`；代码、测试、迁移、diff 和运行日志属于实际产物或证据，不算过程文档。

**分支工作流硬限制：工作单元最早可在 `01` 需求整理阶段创建，并可独立推进到客户端对接和 `07-Uxx` Review；不存在“所有分支先汇合才能 review”的门禁。当前阶段若发现真实独立范围，仍可继续拆分稳定工作单元 `U01`、`U02`……；所有文件保持在同一个已解析的功能目录，不增加分支子目录。没有真实分支时继续使用原文件名。第一次拆分创建 `00-工作流索引.md`，只记录 ID、范围、依赖、当前阶段、当前文档和整体 Review 指针；拓扑只由依赖表达。分支文档命名为 `06-<Uxx>-<主题>-完整实现方案.md`。当前 Uxx 只检查自己的共享需求基线、自身/祖先需求文档和真实依赖；无依赖兄弟工作单元不构成阻塞。**

在分支工作流中，下述“本阶段唯一文档”指当前工作单元的唯一 `06` 权威文档。`00-工作流索引.md` 只做路由；一个工作单元完成后可以在满足自身门禁时进入 `07-Uxx` Review；这不代表其他工作单元完成，也不代表已经需要或可以开始整体 `07-交叉评审.md`。

**文档更新时序：新事实改变本阶段内容时，默认同轮原位更新唯一文档并告知路径；用户约定集中回写时按约定执行，交接时说明未落盘内容。需要修正上游时列明影响和拟修改内容，已有授权直接回写，超出授权再确认。**

**结构性变更影响传播：范围、状态、合同、数据权威、依赖或配置真源变化时，核对当前文档元信息、正文、验证与下一动作，并同步真实受影响的上下游、客户端合同和 `00-工作流索引.md`；不扩散到无关分支。**

**完成前一致性检查：依据当前确认和实际证据，清除互斥状态、旧数值与过时结论；证据不足保留待确认或待验证，不宣称完成。**

**阶段切换：开始前核对当前范围真实上游的状态与证据；有缺口时说明影响，按用户约定推进并保留未决事实。满足本阶段完成条件后，更新原有终态并重新读取确认已落盘，不新增审批文档或状态体系。**

存在 `00` 时，开始或恢复本阶段前必须解析当前 `Uxx` 的共享上游和直接前驱，只检查实际依赖；未被依赖的兄弟工作单元不构成阻塞。

**跨 session 可恢复性硬限制：当前工作单元的完整实现方案文档不得依赖当前聊天上下文才能继续实现。** 在开始编码、每个分步 review 边界、暂停或结束当前 session 前，文档必须能明确回答：当前工作单元、实现模式、步骤划分、已确认范围、当前步骤及状态、实际代码基线与关键入口、已完成行为和验证证据、尚未解决的阻塞或决策、下一动作及进入下一步的条件。不得复制共享 `01` 或其他工作单元全文来制造“自包含”；只保留继续实现必需的引用、差异和当前状态。新的 session 必须先用当前文档核对实际代码/diff，发现不一致时以代码事实为依据立即修正文档后再继续。

普通实现正文变化若不改变拓扑、当前阶段或当前文档，不重复改写索引。

## 前置条件与产物

未分支时读取并核对：

- `01-原始需求.md`；
- `02-需求挖掘.md`；
- `03-程序实现澄清.md`；
- `04-配置规划.md`；
- `05-框架实现方案.md`；
- 已存在的 `06-完整实现方案.md`（若有）；
- 已实现骨架、当前 diff、测试和启动结果。

存在 `00` 时，先定位当前 `Uxx`，再读取当前工作单元适用的需求基线 与索引声明的当前工作单元实际 `02`–`05` 依赖和直接前驱、当前 `06`、代码与测试。不得机械读取并等待所有兄弟工作单元。

未分支过程文档：

```text
<文档根目录>/<YYMMDD><feature>/06-完整实现方案.md
```

分支后当前工作单元过程文档：

```text
<文档根目录>/<YYMMDD><feature>/06-<Uxx>-<主题>-完整实现方案.md
```

使用 [完整实现方案模板](references/完整实现方案模板.md)。方案、实现模式、步骤状态、接力点、验证结果和剩余风险都原位更新在当前工作单元这一份文档中。

若当前骨架不能安全运行，先立即在当前 `06` 记录阻塞并告知用户；随后说明拟对当前工作单元对应 `05` 做出的修改，获得用户确认后再回到 `game-scaffold` 修复。

## 工作单元与实现 Step

两者解决不同层级的问题：

- **拆工作单元 `Uxx`**：范围可以独立推进、独立阻塞、由不同 session/Agent 承担，或需要独立的人类 review 生命周期；依赖写入 `00`。
- **文档内 Step**：仍属于同一工作单元，后一步建立在前一步稳定基线上，不能作为独立交付分支；只用于降低一次人工 review 负担。

不得因为实现要分三次 review 就机械创建三个 `Uxx`；也不得把真正可以并行的两个独立功能硬塞成一个 `06` 的 Step。

若到了实现阶段才发现需要真正拆工作单元：

1. 更新或创建 `00`，为直接后继分配新 `Uxx`；
2. 当前父 `06` 只保留共同实现基线并标记 `已拆分`；
3. 若子范围仍继承同一套已确认 `01`–`05`，可直接创建子 `06`；若拆分同时暴露产品、技术、配置或框架决策差异，则子工作单元回到最早受影响的 `02`–`05` 阶段，不得强行从 `06` 开始；
4. 父工作单元停止后续推进，仅索引中的叶子后继继续。

## 工作流程

### 1. 验证当前工作单元框架与基线

开始或恢复实现前检查实际模块、数据结构、主流程、配置、旧数据和上下游是否与当前 `05` 及索引依赖一致；检查当前 `06` 的步骤、代码入口与实际 diff 是否一致。

局部差异可在当前实现方案说明。需要推翻核心边界时，先更新当前 `06` 阻塞，再说明受影响的实际上游文档并取得用户确认。

### 2. 建立当前工作单元需求完成状态

逐条对照当前范围，把每项标为：已由骨架完成、本阶段实现、延期/范围外、外部承载、存在矛盾或缺决策。这些状态只属于当前 `06`，不另建需求矩阵。

### 3. 判断单次实现、分 Step，还是拆工作单元

先判断独立生命周期：若范围可以独立推进/阻塞/review，优先拆 `Uxx`。剩余仍属于同一工作单元时，再判断人工 review 负担：多个可顺序验收的行为闭环、跨多个高影响边界、单次 diff 过大或验证天然分段时，主动推荐 2–5 个 Step。

每个 Step 必须是可单独理解、实现、验证和 review 的纵向行为闭环，不按文件/层级横向切割。Agent 先给建议拆法，再让用户采用或调整。

实现模式和步骤边界确定后立即写入当前 `06` 并告知用户。

### 4. 产出可执行实现方案

按依赖顺序覆盖实际相关的核心规则与状态、配置与数据、权限/资格/资产、副作用、持久化/并发/幂等、失败/补偿/恢复、兼容/发布/回滚、可观测性与测试。描述决策与行为，不粘贴大段最终代码。

分 Step 时在同一当前 `06` 维护步骤表；跨工作单元依赖只在 `00` 维护，不复制兄弟状态。

### 5. 按已约定范围开始实现

向用户展示当前工作单元剩余范围、重要边界、方向变化、实现模式、步骤划分、验证方式和延期项。用户已有适用授权时直接实现，不再次索要形式确认；尚缺会影响实现的决策时说明选项，用户可选择先按明确假设实现。用户部分确认或调整边界时更新当前 `06`。

### 6. 按当前 Step 形成纵向闭环

单次模式连续完成；分 Step 模式默认一次实现当前已确认 Step，用户也可一次授权多个 Step 连续完成。每步完成规则、配置/数据接入、失败与副作用边界、危险占位清理、测试和验证，并按约定时序回写当前 `06` 的实际实现、证据、偏差和接力点。

分 Step 模式默认完成当前步后交给用户 review；若用户已经要求连续完成或最后统一 review，则按该范围继续，不逐步重复确认。只有新事实实质改变已约定范围、风险或假设时才重新确认。Step 级 review 是实现中的检查点，正式交叉 Review 的覆盖另行记录。

### 7. 在 review 或换 session 前写好接力点

任何暂停位置都要让当前 `06` 明确当前工作单元、实现模式、步骤状态、代码基线、关键入口、已完成行为与证据、有效偏差、未决阻塞、下一动作和进入下一步条件。不得依赖聊天记录。

### 8. 完整验证并收敛当前工作单元

根据风险选择单元、集成、回归、启动/升级、并发/幂等、故障、性能等验证。每获得结果立即写回当前 `06`。不能运行的验证说明原因、替代证据和剩余风险。

全部 Step 完成后，用实际实现替换计划描述，删除过时方案和失效风险，保留必要验证摘要、真实延期/范围外和已知风险，把接力点收敛为“当前工作单元实现完成，等待本单元交叉 Review”。

### 9. 更新工作流索引与 review 门禁

当前 `Uxx` 完成后，把 `00` 中它的当前阶段/文档更新到真实状态。当前单元及其真实依赖达到 pre-review 条件后，即可进入 `game-review` 创建 `07-Uxx-<主题>-交叉评审.md`；无依赖兄弟单元尚未完成不构成阻塞。Step 级人工 review 不能替代该单元的正式交叉 Review。

所有本次目标叶单元分别 Review 完成后，才由 `game-review` 判断是否需要整体 `07-交叉评审.md`；仅在存在真实集成风险时执行。

## 完成条件

对当前叶工作单元：

- 已确认范围内需求行为全部有实现或外部承载；
- 分 Step 时所有 Step 均完成，人工 review 按用户约定执行，未执行部分如实标注；
- 骨架危险占位和隐式未完成逻辑已清除；
- 配置、数据、接口、失败、兼容和回滚形成闭环；
- 关键测试和运行验证通过；
- 不存在未标记 P0/P1 实现风险；
- 无尚待确认修订的上游文档阻塞；
- 当前 `06` 与实际代码一致并能供新 session 复核；
- 当前工作单元本阶段没有其他旁支过程文档。

满足这些条件表示当前工作单元可在自身真实依赖满足后进入交叉 Review；不代表其他单元完成，也不代表整体集成 Review 已具备启动条件。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 大需求仍一次给出全部方案并连续实现 | 先判断应拆工作单元还是同一单元分 Step |
| 直接问用户“你想怎么拆” | Agent 先分析依赖并给建议 |
| 按文件/层级切 Step | 按纵向行为闭环切分 |
| 未约定就越过 Step 检查点，或已获连续执行授权仍反复确认 | 按约定范围执行，在约定的 review 点交接 |
| 每个 Step 新建一个实现文档 | 同一工作单元的 Step 全在一份 `06` |
| 真正独立的两块工作只做 Step | 拆成不同 Uxx，并在 00 显式依赖 |
| 依赖上一 session 聊天恢复 | 当前 `06` 保存接力点，先核对代码/diff |
| 实施结束后另写完成报告 | 原位更新当前主文档 |
| 无法执行测试却宣称完成 | 记录限制、替代证据和剩余风险 |
| 实现变化后只在聊天汇报 | 同一轮更新当前 `06` 并告知路径 |
| 无依赖兄弟未完成就阻止当前 Uxx Review | 当前 Uxx 满足自身门禁后进入 `07-Uxx-*` |
| 把一个 Uxx 的 Review 当成整体完成 | 各单元分别 Review 后，再按集成风险决定是否创建整体 07 |
| 为 Uxx 增加子目录 | 禁止增加分支子目录，所有过程文档保持同目录 |
