# 搭建游戏功能框架

开始前读取 [文档与分支规则](references/文档与分支规则.md)，核对当前单元实际依赖的 `01`–`04`、配置待接入项及代码。默认上游状态为 `01=整理完成`、`02/03=已收敛`、`04=已完成`。

使用 [框架实现方案模板](references/框架实现方案模板.md)，每个单元仅维护一份 `05-框架实现方案.md` 或 `Uxx-05-<主题>-框架实现方案.md`；设计、验证和移交均原位维护，代码、Schema、测试与日志作为证据。

## 框架边界

- 只建立数据、持久化、镜像、客户端视图和消息拓扑；权限/资格、扣除/奖励、业务状态转换及产品路径选择交给 `game-implement`。
- 空 RPC 只解析、寻址、转发和返回技术错误；最终权威端在任何业务副作用前返回明确未实现。
- 设计与实现前读取 [数据与消息拓扑](references/数据与消息拓扑.md)，按本次实际路径落实权威、恢复、同步和未就绪行为。
- **框架真实链路硬限制：** 完成须证明 Schema/定义 → 生成或注册 → 暴露/路由 → 权威实体 → 技术失败返回可达；后续运行时配置/属性须定位真实消费入口。字段、导表或内部方法存在不等于客户端可达或接入完成。

## 协作与更新

- **人工协作**：简述框架后，在已有授权内续接 `06`，不强求用户 Review 或跑测；用户限定框架或暂停时遵从。缺口、假设、待补与复核点留在当前 `05`，继续不等于验证通过。
- **分支工作流硬限制：** 按上述参考中的条件询问分支或 Step，仅按用户确认的方案拆分；创建 Uxx 时更新 `00-工作流索引.md`，父 `05` 留共同基线并标记 `已拆分`，由叶后继进入 `06`。
- **文档更新**：默认同轮原位更新事实、证据与已解除阻塞并告知路径；集中回写时交接未落盘内容。
- **结构性变更**：范围、状态、合同、数据权威、依赖或配置真源改变时，同步真实受影响的上下游、客户端合同和 `00`。上游有误先在 `05` 记阻塞、说明拟改内容，已有授权直接修订，超出授权再确认。

## 完成条件

由 Agent 按实际改动验证序列化、启动/恢复、镜像全量/增量/ready、客户端视图、跨线程路由、技术失败及无业务副作用，并记录业务规则移交项。未做必要运行验证时只能标记 `骨架代码已落地，待运行验证`。

核对文档、代码与证据一致性；无未决上游阻塞且验证通过后，顶部写 `骨架已完成`、更新日期并重读确认落盘。仅缺目标环境运行证据时也可保留待验证状态续接 `06`；实际安全问题或未决核心设计先处理。框架落地不代表产品实现完成或可直接进入正式 Review。
