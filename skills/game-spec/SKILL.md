# 整理游戏原始需求

## 新需求前置选择

识别到**新的、需要跨多个研发阶段推进的功能需求**，且用户未明确选择使用或不使用工作台时，先理解必要背景，**在实质建档或大量实现前**适时主动询问一次：

> 这个需求适合用「需求工作台」推进。是否使用？我可以协助需求梳理、关键问题确认、技术方案、功能实现和交叉 Review。
>
> **使用工作台 / 直接处理**

- 选择使用：按用户原任务范围和已有授权选择适用阶段；没有现存阶段产物时从需求整理开始。工作台选择不等于授权额外修改、跳过关键业务决策或宣称验收通过。
- 选择直接处理：按普通任务处理，**同一需求不再重复询问**，不擅自创建工作台阶段文档。用户之后主动要求启用时再按其要求执行。
- 已明确要求某个 Skill 或工作台、继续已有工作台任务、局部解释/评审/修复及单纯可行性咨询：**不询问**，直接执行对应任务。用户改变目标或提出另一项完整新需求时再判断。
- 不为推荐工作台而延迟回答简单问题；也不要把每轮或每个阶段都变成一次流程确认。

仅在用户选择使用工作台、明确要求本 Skill，或沿已有授权继续相关阶段后，读取 [文档位置](references/文档位置.md) 定位文件，使用 [原始需求模板](references/原始需求模板.md) 整理 `01-原始需求.md`。用户选“直接处理”则不进入下述建档步骤。

## 整理规则

- 只整理来源已有需求，不补边界、验收标准或实现方案；保留限定词和明确给出的技术约束。
- 同一事实只写一次，其条件、数值和例外放在一起；不同限定不能因去重而丢失，跨处联系只引用编号。
- 仅明确的修正关系可覆盖对应旧说法；否则保留冲突，不默认最新材料优先。
- 业务语义已明确、只缺可配 ID/数值时，不补值、不列为原文待确认、不阻塞 `01`；具体值、合法范围和字段能力交给 `04` 查真实配置源。若取值改变行为、资格、资产类型、时序、范围或验收，或来源要求固定值，仍属需求未决。
- 正文默认只有“需求规则”；独立主题才分三级标题。仅按需增加“明确排除”“冲突与原文待确认”，不写空章节或“无”。

## 协作与更新

- **人工协作**：用户可调整阶段与回写节奏；沿用已有授权。继续不等于确认或验证通过，缺口、假设、待补项和复核点留在当前文档，不另建审批文件。
- **需求分支硬限制：** 有真实独立推进边界时可从 `01` 拆分；用户要求协作拆分时也按真实边界执行，不强迫先完成整体 `01`。拆分或续接 Uxx 前读取 [分支规则](references/分支规则.md)，维护 `00-工作流索引.md`；单线不创建它。
- **文档更新**：默认同轮原位替换旧结论、删除已解决项并告知路径；约定集中回写时，交接说明未落盘内容。
- **结构性变更**：范围、状态、合同、数据权威、依赖或配置真源改变时，同步实际受影响的上下游、客户端合同及 `00`。回写上游前列明影响和拟修改内容，已有授权直接执行。

## 完成条件

逐条核对来源覆盖与文档一致性。叶文档状态写为 `整理完成` 或 `存在待确认原文`，更新日期并重新读取确认落盘；未决事实不因提前进入 `game-discovery` 而清除。回复文件路径及冲突/待确认项数量。
