# 整理游戏原始需求

读取 [文档位置](references/文档位置.md)，按 [原始需求模板](references/原始需求模板.md) 维护 `01-原始需求.md`，只留需求规则与关键约束。

## 整理规则

- 只整理来源需求及 `02/03` 已确认要点，不补边界、验收标准或实现方案；重整时保留有效结论。
- **精简硬限制：** 删去不影响理解、决策或验收的内容；同一事实只写一次，条件、数值和例外不可丢，不把多条规则挤成长句。
- 仅按明确修正覆盖旧说法；冲突保留待确认，不自行补先后关系或以实现意图消解。
- 业务语义已明确、只缺可配 ID/数值时，不补值、不列为原文待确认、不阻塞 `01`；具体值、合法范围和字段能力交给 `04` 查真实配置源。若取值改变行为、资格、资产类型、时序、范围或验收，或来源要求固定值，仍属需求未决。
- 技术只留关键选择与硬约束，不罗列勘察、既有机制、代码定位、完整合同表或操作清单；配置细节与技术设计交 `04/05`。
- 正文默认只有“需求规则”；按需增加“关键约束”“明确排除”“冲突与原文待确认”，不写空章节。

## 协作与更新

- **人工协作**：用户可调整阶段与回写节奏；沿用已有授权。继续不等于确认或验证通过，缺口、假设、待补项和复核点留在当前文档，不另建审批文件。
- **需求分支硬限制：** 用户明确要求拆分时，可从 `01` 按真实边界执行，不强迫先完成整体 `01`。拆分或续接 Uxx 前读取 [分支规则](references/分支规则.md)，维护 `00-工作流索引.md`；单线不创建它。
- **文档更新**：默认同轮原位替换旧结论、删除已解决项并告知路径；约定集中回写时，交接说明未落盘内容。
- **结构性变更**：范围、状态、合同、数据权威、依赖或配置真源改变时，同步实际受影响的上下游、客户端合同及 `00`。回写上游前列明影响和拟修改内容，已有授权直接执行。

## 完成条件

核对来源覆盖与语义一致性，再删冗余。叶文档状态写为 `整理完成` 或 `存在待确认原文`，更新日期并重读确认落盘；提前进入 `game-discovery` 不清除未决事实。回复路径及冲突/待确认项数量。
