# 挖掘游戏需求

**人工协作优先：阶段门禁、确认点与文档时序是默认方式。用户可跳步、合并确认、按显式假设继续或延后 Review；已有适用授权不重复确认，真实操作权限仍须满足。继续决定不等于验证通过：在当前文档保留实际缺口、依据或假设、待补项与复核点；本规则也适用于随包模板。**

## 目标

基于当前工作单元适用的需求基线、代码和现有实现，找出真正会改变产品规则的遗漏点，通过多轮沟通维护未分支的 `02-需求挖掘.md`，或当前工作单元的 `02-Uxx-<主题>-需求挖掘.md`。

**核心原则：事实自己查，只把产品决策交给需求负责人。**

**可配置值非问题硬限制：若需求语义已经明确，剩余不确定仅是可配置的具体 ID、数量、概率、阈值等内容值，且这些取值不改变行为分支、资格、资产类型、时序、功能范围或验收语义，则不得创建 `02` 问题，也不得追问“具体 ID 是多少 / 发多少”。本阶段只在确有产品意义时确认业务约束，例如“奖励只能来自货币类”；配置 ID 的合法业务域/范围、字段类型和可配能力由 `04` 基于真实配置源收敛，最终内容值留给策划配表。若不同 ID 代表不同业务类别/机制，或具体取值本身会改变产品规则，才属于需求决策。**

**文档职责：未分支时 `01-原始需求.md` 保存全部当前产品规则；分支时由共享需求基线与当前/祖先 `01-Uxx` 共同构成当前工作单元的产品规则；当前 `02` 只保存当前工作单元尚未解决的高价值产品问题、必要风险、明确延期，以及已经回答但尚待用户确认回写 `01` 的最小临时结论。上游回写确认完成后，该临时内容必须从当前 `02` 删除。**

**结构硬限制：一个问题只允许一个连续分块，问题、必要依据和建议放在一起。禁止再建立“已确认结论、当前批次、问题台账、暂不追问、收敛检查”等重复分块。**

**闭环硬限制：每轮沟通结束后立即更新当前阶段文档。已解决、已取消、被覆盖或不再有价值的内容必须移除；部分解决时只保留剩余问题。需要回写 `01` 时，只在原问题分块内保留最小的待回写状态，不另建结论区。**

**分支工作流硬限制：工作单元最早可在 `01` 需求整理阶段创建，并可独立推进到客户端对接和 `07-Uxx` Review；不存在“所有分支先汇合才能 review”的门禁。当前阶段若发现真实独立范围，仍可继续拆分稳定工作单元 `U01`、`U02`……；所有文件保持在同一个 `docs/requirements/<feature>/` 目录，不增加分支子目录。没有真实分支时继续使用原文件名。第一次拆分创建 `00-工作流索引.md`，只记录 ID、范围、依赖、当前阶段、当前文档和整体 Review 指针；拓扑只由依赖表达。分支文档命名为 `02-<Uxx>-<主题>-需求挖掘.md`。当前 Uxx 只检查自己的共享需求基线、自身/祖先需求文档和真实依赖；无依赖兄弟工作单元不构成阻塞。**

在分支工作流中，下述“本阶段唯一文档”指**当前工作单元在本阶段的唯一权威文档**；同一阶段可以存在其他工作单元的 `02` 文档。`00-工作流索引.md` 是路由元数据，不属于某个工作单元的阶段正文。

**文档更新时序：新事实改变本阶段内容时，默认同轮原位更新唯一文档并告知路径；用户约定集中回写时按约定执行，交接时说明未落盘内容。需要修正上游时列明影响和拟修改内容，已有授权直接回写，超出授权再确认。**

**结构性变更影响传播：范围、状态、合同、数据权威、依赖或配置真源变化时，核对当前文档元信息、正文、验证与下一动作，并同步真实受影响的上下游、客户端合同和 `00-工作流索引.md`；不扩散到无关分支。**

**完成前一致性检查：依据当前确认和实际证据，清除互斥状态、旧数值与过时结论；证据不足保留待确认或待验证，不宣称完成。**

**阶段切换：开始前核对当前范围真实上游的状态与证据；有缺口时说明影响，按用户约定推进并保留未决事实。满足本阶段完成条件后，更新原有终态并重新读取确认已落盘，不新增审批文档或状态体系。**

存在 `00` 时，上述门禁必须先从索引解析目标 `Uxx` 和实际依赖；未被当前工作单元依赖的兄弟分支不构成阻塞。索引无法唯一确定目标工作单元、依赖或当前文档时，先修正索引，不得靠聊天记忆猜测。

普通 `02` 正文变化若不改变拓扑、当前阶段或当前文档，不重复改写 `00`。

## 产物与工作单元

必须先确认当前工作单元适用的共享需求基线与自身/祖先 `01-Uxx` 已达到当前阶段所需的可移交状态。

未分支时维护：

```text
docs/requirements/<feature>/02-需求挖掘.md
```

分支后当前工作单元维护：

```text
docs/requirements/<feature>/02-<Uxx>-<主题>-需求挖掘.md
```

使用 [需求挖掘模板](references/需求挖掘模板.md)。文档表示当前状态，不保存问答流水。

需要拆分时，Agent 先判断是否真的存在多个可独立推进/阻塞/review 的产品问题域。若用户已明确要求拆分，按最短依赖模型执行；否则先给出建议工作单元及依赖并获得用户确认。通常控制在 2–5 个直接后继，不为每个小问题创建工作单元。

若在已有当前 `02` 上继续拆分：

1. 第一次拆分先创建 `00-工作流索引.md`，已有则原位更新；
2. 为所有后继分配新的稳定 `Uxx`；
3. 当前父文档只保留仍有效的共同基线，顶部状态改为 `已拆分`；
4. 分支专属未决问题移动到对应子 `02`，共享事实通过 `01` 或父文档引用，不复制正文；
5. 父工作单元不再直接创建 `03`，只由索引中的叶子后继继续。

## 职责边界

可以询问会改变玩家行为、规则、范围、资产、资格、时序、失败结果、跨系统关系或运营兼容的产品决定。

不要询问类、模块、表、协议、缓存、存储、并发实现、接口命名和其他不改变产品结果的技术选择。代码能回答的事实不得转问负责人。

## 工作流程

### 1. 定位工作单元并调查事实

若存在 `00`，先读取索引定位当前 `Uxx`、范围、实际依赖和当前文档；否则按未分支路径处理。随后读取 `01`、当前工作单元相关代码、配置、协议、测试、历史行为和现有待确认事项。代码细节只用于判断影响，不写成长篇背景。

如果调查证明当前范围应拆成独立工作单元，按“产物与工作单元”的规则先完成拆分和索引更新，再继续提问；不得在一份 `02` 中长期混合多个可以独立推进的分支。

### 2. 筛选问题

问题只有同时满足以下条件才进入当前工作单元文档：

1. 答案可能改变产品行为、范围、资产、安全或验收；
2. 需求负责人拥有决定权；
3. 现有资料无法可靠回答；
4. 影响值得沟通；
5. 不是重复问题或实现细节；
6. 属于当前工作单元范围，而不是兄弟工作单元。

如果一个问题只是在追最终配置内容值（例如某个货币 ID、奖励数量、概率或平衡阈值），先判断其业务类别/约束是否已经明确。只要配置能力可以承载且不同取值不改变产品规则，就直接过滤掉，不进入 `02`；需要确认的只是会改变产品语义的类别或边界。

优先级：P0 为核心矛盾或重大资产/公平风险；P1 为主要流程和重要边界；P2 仅在确有价值时保留。

### 3. 按问题聚合

每个问题分块最多包含：

- ID、优先级、状态；
- 一个可直接回答的问题；
- 理解该问题所必需的需求或代码依据；
- 明显低风险时的一条建议。

同一问题的信息必须相邻，不按依据、状态、结论等维度拆到其他章节。

### 4. 分轮沟通

每轮提出 1–3 个强相关问题，按依赖顺序推进。分支较大时一次只问一个，不批量堆积低价值边界。

### 5. 回答后立即更新当前阶段

收到回答后，在同一轮完成：

1. 立即原位更新当前 `02` 文档；
2. 部分解决时重写原分块，只保留剩余缺口；
3. 已取消、已默认、价值下降或失效的问题直接移除；
4. 清理因答案变化而失效的其他内容；
5. 仅在产生新的高价值缺口时新增问题；
6. 在回复中明确告知当前 `02` 的完整路径已更新。

若答案形成需要写入当前工作单元适用的需求基线 的产品规则：

若用户已经确认该结论并授权回写，直接更新适用的 `01`、清理当前 `02` 的重复内容并告知路径，不再重复询问。尚无适用授权时采用以下默认流程：

1. 先说明拟修改内容，不静默改写用户尚未确认的规则；
2. 在原问题分块内将状态压缩为“已回答，待确认回写 `01`”，只保留拟回写的最小结论；
3. 主动向用户说明拟修改 `01` 的具体位置和内容，并请求确认；
4. 用户确认后，立即更新 `01`，明确告知用户 `01` 已更新；
5. 随后立即从当前 `02` 删除该临时待回写内容，并再次告知当前 `02` 已更新。

过程追溯由版本历史承担，当前文档不保留旧问题、旧选项和旧答案。

### 6. 更新路由元数据

只有发生以下变化时才同步更新 `00`：

- 新建、拆分或终止工作单元；
- 当前工作单元进入新的阶段；
- 当前权威文档路径变化；
- 工作单元依赖关系变化。

不得把当前问题、P0/P1 数量、答案或状态摘要复制进 `00`。

## 可选保留内容

只有三类内容可在普通待确认问题之外保留：

- 需求负责人明确延期、未来仍需产品决策的事项；
- 足以影响范围、工期或可行性，需要程序评估的重大风险；
- 已回答但尚待用户确认回写 `01` 的最小临时结论。

没有内容时不创建章节，也不写“无”。待回写内容必须留在原问题位置，不能集中成独立章节。

## 收敛条件

对当前叶工作单元：

- 无未解决 P0/P1 产品问题；
- 无尚未确认回写 `01` 的临时结论；
- 当前范围的核心规则可唯一理解；
- 重大技术风险已移交；
- `01` 已在用户确认后吸收全部有效产品结论；
- 当前 `02` 不再重复已确认规则。

结束时只更新当前文档顶部状态并说明该工作单元能否进入程序实现澄清，不生成结论摘要。某个工作单元收敛不代表兄弟工作单元已完成，也不代表整个功能可以进入 `game-review`。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 同一问题出现在当前批次、结论表和台账 | 只保留一个连续问题分块 |
| 回答后在旧问题下面继续追加 | 立即压缩当前分块；需要回写 `01` 时先请求确认 |
| 无授权时静默改写 `01`，或已有回写授权仍再次询问 | 复用已有确认；仅对新增决策或超出范围的修改询问 |
| 部分解决仍保留完整旧问题 | 只留下尚未明确的部分 |
| 建立“暂不追问”垃圾桶 | 无决策价值的内容直接移除 |
| 追问可配的具体 ID/数量/概率 | 只确认会改变产品语义的业务类别/约束；具体合法范围与最终值交给 04/策划配表 |
| 把代码阅读问题转问策划 | 先调查，只有产品决策才问 |
| 只在聊天里说结论，未更新当前 `02` | 同一轮更新当前工作单元文档并明确告知路径 |
| 无实际独立工作却预建 U01/00 | 保持未分支旧文件名，只有真正拆分时才创建索引 |
| 为 U01/U02 创建子目录 | 所有工作单元文件保持在同一 feature 目录 |
| 用 U01.1/U01.2 表达父子关系 | 分配新的稳定 Uxx，父子与串并行统一写在 00 的依赖中 |
| 兄弟分支未完成就阻塞当前分支 | 只检查当前 Uxx 的实际依赖 |
