# 挖掘游戏需求

开始时读取 [文档位置](references/文档位置.md)，按 [需求挖掘模板](references/需求挖掘模板.md) 维护 `02-需求挖掘.md`。

**分支工作流硬限制：** 存在 `00-工作流索引.md` 或用户要求拆分时，先读 [分支规则](references/分支规则.md)。仅检查本单元真实依赖，不等兄弟分支汇合。

## 提问与收敛

1. 读取适用 `01`、现有问题和相关代码事实；默认叶需求须 `整理完成`。上游有缺口先说明影响并返回上游，已有继续约定则按约定推进。
2. 只问资料不能回答、属于本单元且需负责人决定的高价值产品问题。技术选择交给 `03`，可查事实自己查；低价值边界直接删除，不建“暂不追问”区。
3. 语义已明确、仅缺可配 ID/数值，不创建问题；合法范围和字段能力交 `04` 查配置源，最终值交策划配表。取值改变行为、资格、资产类型、时序、范围或验收时，才问业务约束。
4. P0 为核心矛盾或重大资产/公平风险，P1 为主流程与重要边界，P2 仅留有决策价值者。每轮按依赖问 1–3 个相关问题，复杂问题单独问；不为凑批次追加问题。
5. 每题只保留一个连续分块：问题、必要依据及明显低风险时的建议。`01` 保存有效产品规则，`02` 只存未决问题、待移交的重大技术风险、负责人明确延期项及最小待回写结论；不另建摘要或台账。

## 协作与更新

- **人工协作**：用户可调整阶段、确认与回写节奏；沿用已有授权。继续不等于确认或验证通过，缺口、假设、待补项与复核点留在当前文档，不另建审批文件。
- **结构性变更**：范围、状态、合同、数据权威、依赖或配置真源改变时，同步实际受影响的上下游、客户端合同和 `00`，不扩散到无关分支。
- **文档更新**：默认同轮原位更新 `02` 并告知路径；部分解决只留剩余缺口，删除取消、失效或低价值项。约定集中回写时，交接说明未落盘内容。
- 答案形成产品规则时，列明拟改 `01` 的位置与内容；已有确认及回写授权直接执行，否则在原问题处保留“已回答，待确认回写 01”的最小结论并请求确认。保留必要条件、理由与证据引用，回读核对完整并更新实际引用后，从 `02` 删除对应临时内容；已移交风险同样删除，不保留旧问答。

## 完成条件

核心规则可唯一理解、无未解决 P0/P1 或待回写结论、重大技术风险已移交、有效产品结论已进入 `01` 后，才可标记 `已收敛`。核对文档一致性，更新状态、计数与日期；无剩余事项时删除正文及空章节，仅保留顶部元信息。重新读取确认落盘，回复路径及能否进入 `03`，不另写结论摘要。
