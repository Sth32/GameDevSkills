# 生成服务端到客户端对接文档

**人工协作优先：阶段门禁、确认点与文档时序是默认方式。用户可跳步、合并确认、按显式假设继续或延后 Review；已有适用授权不重复确认，真实操作权限仍须满足。继续决定不等于验证通过：在当前文档保留实际缺口、依据或假设、待补项与复核点；本规则也适用于随包模板。**

## 文档位置

- 只在本技能执行时读取目标项目根目录的可选 `.sth32-game-skills.json`；`documentRoot` 是相对该项目根目录的非空路径。项目根目录取用户指定的目标项目或代码仓库，不是技能安装目录或终端当前目录；目标不明确时先确认。
- 新建文档按“本次明确指定 → 配置中的 `documentRoot` → `Workbench`”选择位置。用户直接指定功能目录时直接使用，不再追加 `requirements/<feature>`；其余情况下过程文档放在 `<文档根目录>/requirements/<feature>/`，长期文档放在 `<文档根目录>/features/<feature>.md`。直接指定长期文档文件时使用该文件；仅指定过程功能目录不改变长期文档目录。
- 继续已有功能时，阶段、Uxx、Review、对接和配表说明都沿用已有功能目录；已有同主题长期文档沿用原文件。改变配置不自动搬迁或复制文档，只有明确要求迁移才移动并更新引用。下文路径示例仅用于新建。
- 未提供文件或字段时使用默认值，不自动创建配置。需要读取的配置若 JSON 格式错误或字段为空、非字符串、非相对路径，说明问题并停止依赖该配置的新建写入，不静默回退。只支持项目配置与对话指定，不读取环境变量或个人配置，也不把设置写入 AGENTS.md。

## 目标

从当前服务端事实出发，生成或更新简洁的客户端对接文档，让客户端明确同步属性、实体生命周期、RPC/事件和数据充分性。未分支时维护 `<本次主题名>-客户端对接文档.md`；分支工作流中维护当前工作单元的 `Uxx-<本次主题名>-客户端对接文档.md`。

**核心边界：描述 Server 提供的合同，不设计客户端内部架构。**

**客户端合同可达性硬限制：客户端对接文档只能描述能够从实际客户端可见 Schema/Defs/生成协议、Observer/View/Event 或 RPC 注册与调用链证明的合同。服务端存在同名方法、内部 Host/View、线程路由或测试桩都不能单独证明客户端可见或可调用。每个新增/变化 RPC、事件和属性至少核对“定义 → 生成/注册 → 客户端可见载体 → 服务端接收/权威处理”的真实路径；任一环缺证据就写成缺口，不得包装成已交付能力。**

**目录与命名硬限制：对接文档必须放在本次需求已有 `01` 至 `06` 阶段文档所在的同一个 `<文档根目录>/requirements/<feature>/` 目录，禁止为工作单元另建子目录。未分支时文件名为 `<本次主题名>-客户端对接文档.md`；存在 `00-工作流索引.md` 且当前合同属于某个工作单元时，文件名必须为 `<Uxx>-<本次主题名>-客户端对接文档.md`。主题名沿用当前工作单元或共同需求已有名称，不得临时换同义名。**

**单文档硬限制：当前工作单元的客户端对接阶段只能维护一份对接过程文档。** 不得为同一工作单元另建属性清单、RPC 清单、生命周期说明、服务端缺口报告、客户端待办或变更摘要。不同工作单元可以分别拥有自己的对接文档；拆分前已存在的共享对接文档可以作为共同基线保留。

**分支工作流硬限制：工作单元最早可在 `01` 创建，并可独立推进客户端对接与 `07-Uxx` Review。当前 Uxx 的服务端属性/RPC/事件合同稳定到足以对接时即可创建或更新自己的 `Uxx-<主题>-客户端对接文档.md`，不等待无依赖兄弟分支。若调查证明范围需要继续拆分，也可更新 `00-工作流索引.md` 创建新 Uxx。所有文件保持同目录；ID 只表达身份，依赖只写在 `00`。分支对接文档只记录当前 Uxx 的合同，拆分前共享合同通过引用继承。**

在分支模式下，下述“本阶段唯一文档”指当前工作单元的唯一客户端对接文档；`00` 是路由元数据，不复制字段、RPC、缺口或验证结论。

**文档更新时序：新事实改变本阶段内容时，默认同轮原位更新唯一文档并告知路径；用户约定集中回写时按约定执行，交接时说明未落盘内容。需要修正上游时列明影响和拟修改内容，已有授权直接回写，超出授权再确认。**

**结构性变更影响传播：范围、状态、合同、数据权威、依赖或配置真源变化时，核对当前文档元信息、正文、验证与下一动作，并同步真实受影响的上下游、客户端合同和 `00-工作流索引.md`；不扩散到无关分支。**

**完成前一致性检查：依据当前确认和实际证据，清除互斥状态、旧数值与过时结论；证据不足保留待确认或待验证，不宣称完成。**

**阶段切换：开始前核对当前范围真实上游的状态与证据；有缺口时说明影响，按用户约定推进并保留未决事实。满足本阶段完成条件后，更新原有终态并重新读取确认已落盘，不新增审批文档或状态体系。**

存在 `00` 时，开始或恢复对接前必须先解析当前 `Uxx` 的实际服务端依赖；未被依赖的兄弟工作单元不构成阻塞。对接文档可以在当前 `Uxx` 属性/RPC 骨架稳定后提前生成，并在该工作单元完整实现后原位更新。

普通合同正文变化若不改变拓扑、当前阶段或当前文档，不重复修改索引。

## 输入与产物

优先核对当前工作单元相关的：

1. 当前服务端属性 Schema、协议/RPC/事件定义和实际代码；
2. 生成后的类型或协议定义；
3. 当前工作单元实际 `05`、`06` 与当前 diff；
4. 当前工作单元适用的需求基线、对应需求/配置文档和拆分前共享合同（若有）。

存在 `00` 时先定位 `Uxx`、范围、依赖和当前对接文档。代码与对接文档冲突时，以当前服务端实现为准，并同一轮原位修正文档；若冲突证明上游过程文档需修订，先说明拟修改内容并获得用户确认。

未分支过程文档：

```text
<已有阶段文档所在目录>/<主题名>-客户端对接文档.md
```

分支后当前工作单元：

```text
<同一目录>/<Uxx>-<主题名>-客户端对接文档.md
```

使用 [客户端对接文档模板](references/客户端对接文档模板.md)。已有旧版泛化 `客户端对接文档.md` 且确认属于本次主题时，按当前是否分支迁移为规范文件名并删除旧名，禁止同一工作单元保留两个版本。

如果拆分前已有 `<主题名>-客户端对接文档.md`，它可以继续作为共享合同基线；各 `Uxx` 文档只写当前分支新增或变化的字段、生命周期和接口，不复制共享基线。只有共享合同本身变化时才更新共享文档。

## 文档范围

### 必须包含

- 当前工作单元新增或变化的客户端可见实体、属性和属性组；
- 服务端权威来源与实际同步实体/组件；
- 全量、增量、按需返回或广播方式；
- 属性类型、单位、枚举、缺省/空值语义；
- 实体生命周期中的同步变化；
- 客户端发起 RPC 的时机、参数、回包和后续推送；
- 服务端主动事件/推送的触发条件与参数；
- 客户端完成表现仍缺少的服务端数据或未确认合同。

### 不要展开

- 客户端 MVC、UI 层级、状态管理、缓存和代码目录；
- 动画、资源加载、交互组件的具体实现；
- 与客户端合同无关的服务端线程、持久化和算法细节；
- 完整服务端调用栈、所有内部属性或整份协议 Schema；
- 没有证据的客户端轮询、补算或容错方案；
- 兄弟 `Uxx` 的合同正文或工作状态。

## 工作流程

### 1. 定位目录、工作单元与合同范围

先定位本次需求已有阶段目录；存在 `00` 时确认当前 `Uxx` 与依赖，选择规范文件名。随后搜索当前工作单元涉及的属性同步、生命周期、RPC/事件、配置/资源 ID 和错误语义。

若调查证明合同范围本身需要拆成独立工作单元，先按 DAG 规则更新 `00` 并分配稳定 `Uxx`，再分别生成对接文档；不得用多个无 ID 的同名文档代替工作单元模型。

### 2. 按合同聚合属性同步

对每个属性或紧密相关属性组，在同一连续分块写清实体/标识、字段/类型/语义、权威者、同步载体、首次获得、增量触发、生命周期清除/重同步和可见范围。每完成或修正一个合同立即更新当前文档并告知路径。

### 3. 按接口聚合 RPC 与事件

每个 RPC/事件同一分块说明方向、发送/接收、触发时机、参数、同步回包、异步结果、错误语义以及客户端确实需要处理的重复/超时/顺序。复杂结构仅给最小示例。

### 4. 检查实体生命周期

检查当前工作单元实际相关的登录、创建、进入视野、变化、销毁、离开视野、权限变化、重连和跨场景场景。结果写回对应属性/接口附近，不另建重复清单。

### 5. 做客户端数据充分性检查

确认客户端仅依据当前工作单元合同 + 明确引用的共享基线即可识别实体、更新/移除表现、展示关键状态、正确调用并关联结果、区分错误状态、找到展示资源。

数据不足时在最相关合同分块记录“服务端缺口”，说明影响和应回退的具体 `Uxx` 阶段；不得另建缺口报告或让客户端猜测。

### 6. 原位压缩并核对

交付前核对实际字段名、类型、触发时机、可见范围、错误语义、目录、`Uxx` 和文件名。沟通或实现变化后立即替换旧内容，删除已解决缺口、旧字段和失效说明。

### 7. 更新索引与 Review 路由

只有工作单元/依赖/当前阶段/当前文档变化时更新 `00`。对接文档完成只表示当前合同可移交；当前 Uxx 的其余 pre-review 条件和真实依赖满足后，可独立进入 `07-Uxx-*`，不等待无依赖兄弟。整体 Review 在各目标叶单元分别 Review 后按集成风险判断。

## 完成条件

- 对接文档与所有过程文档位于同一 feature 目录，无分支子目录；
- 未分支使用 `<主题名>-客户端对接文档.md`，分支使用 `<Uxx>-<主题名>-客户端对接文档.md`；
- 客户端可见属性、生命周期、同步来源、首次/增量触发明确；
- RPC/事件时机、参数、回包、异步结果和错误语义明确；
- 服务端权威与同步载体没有混淆；
- 当前工作单元数据足以支撑表现，或缺口明确路由回具体上游；
- 无尚待确认修订的上游文档阻塞；
- 文档与当前服务端代码、协议和生成定义一致；
- 当前工作单元只有一份规范对接文档。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 为 Uxx 新建目录 | 所有对接和阶段文档留在同一 feature 目录 |
| 两个分支争用同一 `<主题>-客户端对接文档.md` | 分支模式使用 `Uxx-<主题>-客户端对接文档.md` |
| 每个分支复制拆分前完整共享合同 | 保留共享基线，Uxx 只写新增/变化合同 |
| 为属性、RPC、生命周期分别建文档 | 当前工作单元只保留一份对接文档 |
| 数据不足另写服务端缺口报告 | 在相关合同分块记录并路由回具体阶段 |
| 只抄属性 Schema | 补首次同步、变化触发、清除和可见范围 |
| 只写 RPC 名称和参数 | 补发送时机、回包、异步结果和错误语义 |
| 深入设计客户端 UI 和代码 | 只描述 Server 合同 |
| 合同变化后只在聊天说明 | 同一轮更新规范文档并告知完整路径 |
| 当前 Uxx 合同完成就宣布整体可 review | 先核对当前 Uxx 的实现与依赖并独立 Review；整体 Review 在各目标叶单元分别 Review 后按风险判断 |
