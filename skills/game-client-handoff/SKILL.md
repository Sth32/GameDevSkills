# 服务端到客户端对接

先读 [文档位置](references/文档位置.md)，使用 [客户端对接文档模板](references/客户端对接文档模板.md)。单线写 `<主题>-客户端对接文档.md`，分支写 `Uxx-06-<主题>-客户端对接文档.md`，主题沿用已有名称；每个单元只保留一份，缺口也在其中。

## 合同证据

**客户端合同可达性硬限制：** 逐项证明“Schema/Defs 定义 → 生成/注册 → 客户端可见载体 → 服务端接收/权威处理”。同名方法、内部 Host/View、线程路由或测试桩不能证明客户端可见/可调用；缺环即缺口，不写成已交付能力。

先核对当前属性/协议与生成物、服务端代码、实际 05/06 和需求基线。冲突时以已证实的当前实现修正文档，不臆造客户端轮询、补算或容错。只写服务端提供的合同，不设计客户端架构。

写合同前读 [合同检查](references/合同检查.md)，按属性组或接口集中记录生命周期与错误语义，避免重复清单。

## 分支与协作

- **分支工作流硬限制：** 存在 `00-工作流索引.md` 时先解析当前 Uxx 及真实依赖。合同足够稳定即可对接，`06` 只排序，不等待无依赖兄弟；已有共享合同仅引用，分支只写新增/变化。需要拆分时读 [分支规则](references/分支规则.md)。
- **人工协作**：用户可调整阶段和回写节奏；沿用已有授权。缺口、假设、待补项及复核点写在当前文档，不另建审批文件；继续不等于验证通过。
- **文档更新**：默认同轮替换旧合同、删除已解决缺口并告知路径；集中回写时交接说明未落盘内容。需修正上游先列明影响和拟修改内容，已有授权直接执行。
- **结构性变更**：同步实际受影响的上下游和合同；仅单元、依赖、当前阶段或文档指针改变时更新 `00`。

## 完成检查

核对文档与定义、生成物及运行路径的一致性，并验证客户端仅凭当前合同和共享基线能识别实体、更新/移除表现、关联异步结果、区分错误并找到资源。缺数据时在相关合同写“服务端缺口”、影响及回退的具体 Uxx/阶段。

合同可移交须消除阻塞性缺口及待修订上游；按人工约定提前交付时说明限制，不宣称实现或完整游戏验收通过。更新元信息并重新读取确认。当前单元其余 pre-review 条件满足后可独立进入 Uxx-07，整体 Review 在目标叶单元分别评审后按集成风险决定。
